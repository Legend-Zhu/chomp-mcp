> ## 项目定位
> 为 scse-agent（以及任何遵循 MCP 协议的 LLM 客户端）提供"开箱即用、自带摘要（digest）"的联网调研能力。解决 LLM agent 的"信息茧房"问题：当用户需求涉及 agent 不熟悉的外部框架、开源项目、依赖库、API、最新技术时，agent 可以通过本 MCP server 联网调研，并直接拿到结构化的精炼结论，而不是一堆原始网页链接。
> 
> 核心理念：**调用方永远收到精炼摘要，绝不收到原始网页正文**，从而避免长内容污染 agent 上下文。
> 
> ## 技术栈
> - 语言：TypeScript（Node.js 18+），ESM 模块
> - MCP 协议：@modelcontextprotocol/sdk，stdio 传输（JSON-RPC over stdin/stdout）
> - 无任何付费第三方 API 依赖；零 API key 要求（除最后的 LLM 摘要复用调用方配置的 LLM）
> 
> ## 架构：Search → Scrape → Deduplicate → LLM-Synthesize 四段 pipeline
> 
> 本 MCP server 的核心是一条可复用的调研 pipeline，所有对外工具都基于这条 pipeline 构建：
> 
> 1. **Search（搜索）**：调用 SearXNG 元搜索引擎（聚合 Google/Bing/DuckDuckGo 等多个引擎结果），获取候选结果列表（标题、URL、摘要片段）。SearXNG 零 API key、零费用、隐私友好。
> 
> 2. **Scrape（抓取）**：对候选 URL 并发抓取网页正文。主路径使用轻量纯 Node 方案：HTTP 请求 + cheerio 解析 HTML + @mozilla/readability 提取正文（Firefox 阅读模式同款算法）。遇到需要 JavaScript 渲染的页面（如部分 SPA 文档站点），降级使用 Puppeteer 无头浏览器渲染后再提取。每页正文做长度截断（可配置上限，默认每页 8000 字符），防止单页过长。
> 
> 3. **Deduplicate（去重降噪）**：搜索结果常有同一内容多源转载（同一篇文章出现在多个博客/CSDN/掘金）。先做 URL 规范化（去 tracking 参数、统一协议、去 fragment），再做内容级去重（基于段落指纹，如对正文分段后取 hash 集合比对相似度，相似度超阈值的视为重复只保留得分最高的一条）。去重是保证后续摘要质量的关键——不降噪会被噪音淹没。
> 
> 4. **LLM-Synthesize（LLM 摘要）**：把去重后的多段正文喂给 LLM，产出针对原始查询的结构化摘要。这是整个 pipeline 的灵魂：LLM 不是简单拼接，而是综合多个来源、去伪存真、提炼出"这个问题/这个库/这个技术的关键事实、核心用法、集成方式、注意事项"。摘要格式为结构化文本，包含：直接回答（Answer）、关键要点（Key Points）、来源引用（Sources，含 URL）。**LLM 配置通过环境变量注入**（见下方配置），MCP server 内部调用 LLM，调用方无需关心。
> 
> ## 对外工具（MCP tools）
> 
> 本 MCP server 对外暴露两个工具，二者都内置完整或部分 pipeline，且都内置 LLM Synthesize，调用方永远拿到精炼结果：
> 
> ### 工具 1：web_search
> - 用途：对一个查询（query）做完整联网调研，返回结构化摘要。这是主工具，覆盖"我不了解 X，帮我查清楚"的场景。
> - 参数：
>   - `query`（string，必填）：调研查询，例如 "如何用 TypeScript 实现 MCP server"、"RuoYi-Vue3 最新版本如何集成 MyBatis-Plus"
>   - `max_results`（integer，可选，默认 5）：从 SearXNG 拉取并进入 pipeline 的最大候选结果数（影响耗时和摘要质量，建议 3-8）
>   - `focus`（string，可选）：调研焦点提示，引导摘要侧重某个方面，例如 "集成步骤" / "API 用法" / "版本兼容性"
> - 返回：结构化摘要文本（Answer + Key Points + Sources），非原始网页。
> 
> ### 工具 2：web_fetch
> - 用途：对一个已知的具体 URL 做抓取 + 摘要，返回该页关键信息。覆盖"我已经知道要看这个文档/repo/页面，帮我提取要点"的场景。
> - 参数：
>   - `url`（string，必填）：目标 URL
>   - `focus`（string，可选）：提取焦点，例如 "安装方法" / "配置参数" / "CHANGELOG"
> - 返回：该页的结构化摘要文本，非原始正文。

> ## 模块划分
> 
> 本项目按职责拆分为以下模块（供需求阶段进一步细化 User Stories）：
> 
> ### 模块 SR（search-retrieval）：搜索获取
> 负责调用 SearXNG、解析返回的 JSON、规整成统一的候选结果结构（title/url/snippet/score）。处理 SearXNG 公共实例不可达时的错误、超时、重试。支持通过环境变量切换到自托管的 SearXNG 实例。
> 
> ### 模块 SC（scrape-extract）：抓取提取
> 负责把 URL 转成纯文本正文。主路径 cheerio+readability，降级路径 Puppeteer。处理 HTTP 错误（404/403/超时）、编码识别、正文长度截断、非 HTML 资源（如直接是 JSON/XML 的 API 文档）的特殊处理。
> 
> ### 模块 DD（deduplicate）：去重降噪
> 负责 URL 规范化和内容级去重。URL 规范化：去 utm_* 等 tracking 参数、统一大小写、去 fragment、统一尾斜杠。内容去重：对正文分段、计算段落指纹、比对相似度、合并近重复项。
> 
> ### 模块 SY（synthesize）：LLM 摘要
> 负责与 LLM 交互产出结构化摘要。封装 LLM 客户端（OpenAI 兼容接口），管理摘要 prompt（要求产出 Answer/Key Points/Sources 结构、要求引用来源 URL、要求简洁），处理 LLM 调用失败、超时、token 超限（分批摘要后再合并）。
> 
> ### 模块 PL（pipeline-orchestration）：编排层
> 负责把上述四段编排成完整的 web_search 工具流程，以及 web_fetch 的子流程（Scrape→Synthesize）。管理并发抓取的并发度限制、整体超时、错误隔离（单个 URL 失败不影响整体）。
> 
> ### 模块 MC（mcp-server）：MCP 服务入口
> 负责 MCP server 的生命周期：stdio transport 监听、JSON-RPC 消息处理、工具定义注册（web_search/web_fetch 的 inputSchema）、工具调用分发到 PL 编排层、工具响应格式化。这是 scse-agent（或任何 MCP 客户端）连接的入口。

## Project Overview

**chomp-mcp** is an MCP (Model Context Protocol) server that provides "out-of-the-box, digest-enabled" web research capabilities for LLM agents and any MCP-compatible client. It solves the "information cocoon" problem: when a user's needs involve external frameworks, open-source projects, dependency libraries, APIs, or cutting-edge technologies the agent is unfamiliar with, the agent can research the web through this MCP server and receive structured, refined conclusions — not a pile of raw web links.

**Core philosophy:** The caller always receives a refined digest, never raw web page content, preventing long content from polluting the agent's context window.

### Architecture: Search → Scrape → Deduplicate → LLM-Synthesize

The server's core is a reusable research pipeline. Both exposed tools are built on this pipeline:

1. **Search** — Queries the SearXNG meta-search engine (aggregating Google/Bing/DuckDuckGo results) to obtain candidate results (title, URL, snippet). SearXNG requires no API key, is free, and privacy-friendly.
2. **Scrape** — Concurrently fetches page content from candidate URLs. Primary path: HTTP fetch + jsdom + @mozilla/readability. Fallback: Puppeteer headless browser for JavaScript-rendered pages. Content is truncated to a configurable limit (default 8,000 chars/page).
3. **Deduplicate** — URL normalization (strip tracking params, unify scheme/fragment) followed by content-level deduplication (paragraph fingerprinting + Jaccard similarity comparison). Near-duplicates are merged, retaining the highest-scored item.
4. **LLM-Synthesize** — Feeds deduplicated content to an LLM to produce a structured digest (Answer + Key Points + Sources with URLs). Handles token overflow via batch-and-merge. On LLM failure, degrades gracefully to truncated raw content.

### How Modules Interact

```
MCP Client (stdio JSON-RPC)
    │
    ▼
┌─────────────────────────────────┐
│  MC (mcp-server)                │  Tool dispatch, validation, response formatting
│  web_search / web_fetch         │
└──────────────┬──────────────────┘
               │
               ▼
┌─────────────────────────────────┐
│  PL (pipeline-orchestration)    │  Concurrency, timeout, error isolation
│  runWebSearch / runWebFetch     │
└──┬──────┬──────┬──────┬─────────┘
   │      │      │      │
   ▼      ▼      ▼      ▼
  SR      SC      DD      SY
 Search  Scrape  Dedup  Synthesize
```

- **web_search** flows through all four stages: SR → SC → DD → SY
- **web_fetch** flows through two stages: SC → SY

## Getting Started

### Prerequisites

- **Node.js** 18 LTS or later
- **npm** (bundled with Node.js)
- An **LLM API key** (OpenAI-compatible) — required for the synthesis stage

### 1. Install Dependencies

```bash
npm install
```

### 2. Build the Project

```bash
npm run build
```

This runs `tsc` and outputs compiled JavaScript to `dist/`.

### 3. Run the MCP Server

#### Production (compiled)

```bash
LLM_API_KEY="sk-your-api-key" node dist/index.js
```

#### Development (with tsx, no build step)

```bash
LLM_API_KEY="sk-your-api-key" npm run dev
```

### 4. Type-Check (no emit)

```bash
npm run typecheck
```

### 5. Run Tests

```bash
npm test
```

### Environment Variables

All configuration is via environment variables — zero config files.

| Variable | Required | Default | Description |
|----------|----------|---------|-------------|
| `LLM_API_KEY` | **Yes** | — | API key for the LLM service (OpenAI-compatible) |
| `LLM_BASE_URL` | No | `https://api.openai.com/v1` | LLM API base URL |
| `LLM_MODEL` | No | `gpt-4o-mini` | Model name for synthesis |
| `SEARXNG_URL` | No | Public instances | SearXNG search endpoint (self-hosted URL) |
| `SCRAPE_TIMEOUT_MS` | No | `15000` | Per-page scrape timeout (ms) |
| `MAX_CONTENT_CHARS` | No | `8000` | Max content chars per page |
| `MAX_CONCURRENCY` | No | `3` | Concurrent scrape limit |
| `DEDUP_SIMILARITY_THRESHOLD` | No | `0.85` | Jaccard threshold for near-duplicate detection |
| `MIN_PARAGRAPH_CHARS` | No | `20` | Min paragraph length for fingerprinting |
| `DEDUP_EXTRA_TRACKING_PARAMS` | No | (empty) | Comma-separated extra tracking params to strip |

### Self-host SearXNG

`web_search` works best with a self-hosted SearXNG instance. The example below starts SearXNG on `127.0.0.1:8080`, enables JSON responses, and prefers Bing because some public engines may be slow or unavailable in restricted network environments.

Create a local SearXNG directory:

```bash
mkdir -p ./searxng-local
cd ./searxng-local
```

Create `settings.yml`:

```yaml
use_default_settings: true

server:
  secret_key: "<REPLACE_WITH_RANDOM_SECRET>"
  limiter: false
  image_proxy: false

search:
  safe_search: 0
  autocomplete: ""
  formats:
    - html
    - json

ui:
  static_use_hash: true

outgoing:
  request_timeout: 10.0
  max_request_timeout: 15.0

engines:
  - name: bing
    engine: bing
    shortcut: bi

## API Overview

This server exposes two MCP tools via stdio JSON-RPC transport. There are no HTTP REST endpoints — all communication is over stdin/stdout using the MCP protocol.

### Tool: `web_search`

Performs a full web research pipeline (Search → Scrape → Deduplicate → Synthesize) and returns a structured digest.

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| `query` | string | Yes | — | Research query (max 500 chars) |
| `max_results` | integer | No | `5` | Max candidate results from SearXNG (recommended 3–8) |
| `focus` | string | No | — | Research focus hint to guide the digest (max 500 chars) |

**Returns:** Structured digest text containing:
- **Answer** — Direct synthesized answer to the query
- **Key Points** — Bullet list of key findings
- **Sources** — Referenced URLs with titles

### Tool: `web_fetch`

Fetches a specific URL and synthesizes a structured digest of its content (Scrape → Synthesize).

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| `url` | string | Yes | — | Target URL to fetch and summarize |
| `focus` | string | No | — | Extraction focus hint (max 500 chars) |

**Returns:** Structured digest text (same format as `web_search`).

### Response Format

All tool responses are MCP-standard `content` arrays with `type: "text"`. The text content is the structured digest. Error responses use `isError: true` with a human-readable error message. Responses exceeding 25,000 characters are truncated with a marker.

## Module Overview

### MC — MCP Server (`src/modules/mcp-server/`)

The MCP protocol entry point. Manages server lifecycle, stdio transport, tool registration, parameter validation (Zod), and tool-call dispatch to the pipeline-orchestration layer. Wraps all handlers in try/catch to ensure server stability.

**Key files:** `server.ts` (lifecycle), `tool-definitions.ts` (tool schemas), `tool-handlers.ts` (dispatch), `validation.ts` (Zod validation)

### PL — Pipeline Orchestration (`src/modules/pipeline-orchestration/`)

The end-to-end pipeline coordinator. Orchestrates the Search → Scrape → Dedup → Synthesize flow for `web_search` and the Scrape → Synthesize flow for `web_fetch`. Manages concurrency limiting (semaphore-based), overall pipeline timeout (AbortController), and per-URL error isolation.

**Key files:** `orchestrator.ts` (entry + config), `web-search-pipeline.ts`, `web-fetch-pipeline.ts`, `concurrency-limiter.ts`, `timeout-guard.ts`

### SR — Search Retrieval (`src/modules/search-retrieval/`)

SearXNG meta-search client. Sends HTTP GET requests to SearXNG, parses JSON responses, normalizes results (score normalization, URL dedup, field truncation). Supports self-hosted and public instance modes with automatic failover and exponential backoff retry.

**Key files:** `searxng-client.ts` (HTTP client), `response-parser.ts` (JSON parsing), `result-normalizer.ts` (normalization), `retry-failover.ts` (retry logic), `instance-pool.ts` (instance rotation), `errors.ts` (error hierarchy)

### SC — Scrape Extract (`src/modules/scrape-extract/`)

URL-to-clean-text extraction. Primary path: native `fetch` + jsdom + @mozilla/readability. Fallback: Puppeteer headless browser for JavaScript-rendered pages. Handles HTTP redirects, timeouts, charset detection (iconv-lite), content-type routing (HTML/JSON/XML/text/binary), word-boundary truncation, and SSRF protection (private-IP blocking).

**Key files:** `scraper.ts` (orchestrator), `http-fetcher.ts` (HTTP with retry), `content-extractor.ts` (Readability), `puppeteer-renderer.ts` (JS rendering), `content-type-router.ts`, `encoding-detector.ts`, `truncator.ts`, `url-validator.ts`

### DD — Deduplicate (`src/modules/deduplicate/`)

Pure deduplication and denoising transformation. URL normalization strips tracking parameters (utm_*, etc.), unifies scheme/port/fragment. Content-level dedup uses paragraph segmentation, FNV-1a 32-bit fingerprinting, and Jaccard similarity comparison. Near-duplicates are merged via Union-Find, retaining the highest-scored item. Never throws — all errors are caught and logged.

**Key files:** `deduplicator.ts` (pipeline entry), `url-normalizer.ts`, `paragraph-segmenter.ts`, `fingerprinter.ts`, `similarity-computer.ts`, `content-merger.ts`, `stats.ts`

### SY — Synthesize (`src/modules/synthesize/`)

LLM-powered synthesis producing structured digests. Initializes an OpenAI-compatible client, constructs system/user prompts, calls the LLM with retry (exponential backoff for transient errors, separate timeout retries). Handles token overflow via batch-and-merge. On unrecoverable failure, degrades to a fallback digest from raw content. Never rejects a Promise to the caller.

**Key files:** `synthesizer.ts` (orchestrator), `llm-client.ts` (client + retry), `prompt-builder.ts` (prompts), `response-parser.ts` (multi-strategy parsing), `batch-merger.ts` (token overflow), `degradation-handler.ts` (fallback), `token-estimator.ts` (EN/CJK aware)

### Shared (`src/shared/`)

Cross-module type definitions (`SearchResult`, `ScrapeResult`, `ContentItem`, `DeduplicatedItem`, `DigestResult`, `SourceRef`), the `AppError` base class with `ErrorCategory` discriminator, and utility functions (logger, env parsing, semaphore, URL helpers).
